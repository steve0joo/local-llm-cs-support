# Architecture Decision Records (공통)

## 철학
MVP다. 동작하는 최소 구현을 고른다. 서비스·추상화·설정을 미리 늘리지 않는다. 모든 것은 로컬 장비 두 대(Windows RTX 4060 8GB, Mac M4 Pro 24GB)에서 돌아가야 하고, 개인정보는 모델에 닿지 않아야 한다. 잔액조회 영역의 Mac 학습 예외는 BAL-006에 기록한다.

영역별 결정은 `docs/<영역>/ADR.md`에 적는다. 이 문서는 여러 영역에 걸친 결정만 다룬다.

---

### ADR-001: frontend / backend 모노레포 + 영역별 브랜치
**결정**: 저장소 하나에 `frontend/`와 `backend/`를 둔다. 담당 영역마다 `feat-<영역>` 브랜치를 만들고 main으로 PR 머지한다. main PR은 코드 오너인 나(`steve0joo`)나 팀원C(`qhdudedi`) 중 한 명이 승인해야 병합된다(`.github/CODEOWNERS`, main 보호 규칙: 코드 오너 리뷰 필수·승인 1명·관리자 포함). 자기 PR은 스스로 승인할 수 없으므로 내 PR은 팀원C가, 팀원C의 PR은 내가 승인한다.
**이유**: 4명이 계약(API 스키마, 에이전트 인터페이스)을 한 곳에서 함께 본다. 브랜치 이름은 Harness `execute.py`가 만드는 `feat-{task-name}` 규칙과 같다.
**트레이드오프**: 공통 파일(`main.py`, `base.py`)은 충돌할 수 있다. 소유자를 팀원C 한 명으로 정해 줄인다.

### ADR-002: 프론트엔드는 Next.js(App Router) + TypeScript + Tailwind
**결정**: Next.js 단일 페이지 챗봇. 백엔드 호출은 `next.config`의 rewrites로 `/api/chat`을 FastAPI에 프록시한다.
**이유**: Harness 템플릿·TDD 훅이 Next.js 기준이다. rewrites를 쓰면 CORS 설정과 별도 API 라우트 코드가 필요 없다.
**트레이드오프**: 페이지 하나에 비해 프레임워크가 무겁다. 대신 팀 도구와 맞는다.

### ADR-003: 백엔드는 FastAPI 단일 프로세스, 에이전트는 in-process 모듈
**결정**: 게이트웨이·라우터·에이전트 3개·mock API를 FastAPI 앱 하나에 둔다. 영역 경계는 Python 패키지와 `agents/base.py` 인터페이스로 나눈다.
**이유**: 전처리·학습과 같은 언어(Python)다. 서비스를 나누지 않으니 네트워크·배포·장애 지점이 없다.
**트레이드오프**: 영역별로 따로 배포하거나 확장할 수 없다. MVP에는 필요 없다.

### ADR-004: 추론은 Ollama + GGUF로 통일
**결정**: 4개 모델(`cs-router`, `cs-balance`, `cs-loan`, `cs-interest`)을 GGUF(Q4_K_M)로 변환해 Ollama로 서빙한다. 같은 .gguf 파일을 Windows와 Mac에서 쓴다.
**이유**: Mac에는 CUDA가 없다. Ollama(llama.cpp)는 Windows CUDA와 Mac Metal을 모두 지원하므로 Mac에서도 추론까지 로컬로 돈다(PRD 인수 기준 8).
**트레이드오프**: 학습 형식(safetensors)에서 GGUF로 변환하는 단계가 하나 더 생긴다. 변환 후 품질이 떨어지지 않았는지 각 영역이 확인해야 한다. 잔액조회 MLX 산출물의 변환 게이트는 BAL-006을 따른다.

### ADR-005: QLoRA 파인튜닝, 공통 베이스 1종, 영역별 개별 모델
**결정**: Qwen 계열 Instruct 모델 1종을 팀 공통 베이스로 쓴다. 라우터·대출·이자는 Hugging Face Transformers + PEFT + TRL로 QLoRA 학습한 뒤 병합·변환한다. 잔액조회만 Mac MLX LM으로 학습한다(BAL-006). 에이전트 답변 학습 데이터에서는 `output`에 `input`에 없는 수치(금리·금액)나 상품명이 있는 샘플을 뺀다. 답변 생성에 RAG는 쓰지 않는다(2026-09-28 확정).
**이유**: PRD 제약이 "라우터·에이전트 모두 파인튜닝"이다. 데이터셋 모범답변에 섞인 지어낸 값(입력에 없는 금리·금액·상품명)은 정제로 줄인다. 지어낸 사실이 1건이라도 나오면 즉시 불합격이기 때문이다.
**트레이드오프**: 모델 4개가 VRAM 8GB를 나눠 쓴다. 베이스 크기(후보 1.5B~4B급)는 "4개 동시 적재 + 첫 응답 10초"를 만족하는지 벤치마크한 뒤 팀원C가 정리하고 팀이 확정한다. 벤치마크는 실제 요청 경로(라우터 호출 → 에이전트 호출, 비스트리밍)로 잰다. 4개가 한 번에 올라가지 않으면 호출마다 모델을 다시 올리는 시간이 더해지므로 그 경우도 잰다. 10초를 넘기면 베이스를 줄이거나, 4개 영역 학습 데이터를 합쳐 모델 1개로 학습하고 영역은 시스템 프롬프트로 나눈다(학습 데이터 준비는 그대로 각 영역 담당). RAG를 쓰지 않으므로 시간에 따라 바뀌는 정보(금리·상품)는 답하지 않고 상담원 안내로 처리한다.

### ADR-006: 마스킹은 정규식 규칙 기반, 실제 값은 슬롯으로만 전달
**결정**: 주민번호·카드번호·계좌번호·전화번호·주소·금액을 `backend/app/masking`의 정규식 규칙으로 토큰화한다. mock API 값은 프롬프트에 넣지 않고 `slots`로 프론트에 보내 화면에서 치환한다.
**이유**: 결과가 예측 가능하고 테스트하기 쉽다. 모델 기반 개체명 인식(NER)보다 단순하다. "모델은 자리표시자만 다룬다"는 PRD 결정을 구조로 보장한다.
**트레이드오프**: 정규식이 놓치는 형식(띄어 쓴 번호, 한글 숫자 등)이 있을 수 있다. 인수 시나리오에 넣어 테스트로 막는다. 고객 실명은 PRD에서 필수 항목이 아니라 마스킹하지 않는다.

### ADR-007: 비스트리밍 응답
**결정**: `/api/chat`은 완성된 응답을 한 번에 돌려준다. 프론트는 기다리는 동안 입력 중 표시를 보여준다.
**이유**: 슬롯 치환과 선택지 처리가 단순해진다. 작은 양자화 모델이면 10초 안에 완성 응답이 가능하다고 본다.
**트레이드오프**: 첫 글자가 늦게 보인다. 벤치마크에서 10초를 넘기면 스트리밍 도입을 다시 검토한다.

### ADR-008: 공통 데이터 분할은 팀원C가 한 번 만든다
**결정**: `training/common`이 은행 데이터를 걸러내고 `source_id` 기준으로 train/val/test 분할 파일을 만든다. 모든 영역이 같은 분할을 쓴다.
**이유**: 같은 상담에서 나온 QA가 학습·평가에 섞이는 누수를 막는다. 영역마다 기준이 달라지는 것도 막는다.
**트레이드오프**: 에이전트 담당은 분할 파일이 나올 때까지 학습을 시작할 수 없다. 그동안 mock API와 에이전트 로직을 먼저 만든다.
