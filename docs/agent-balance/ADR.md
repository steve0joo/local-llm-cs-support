# ADR: 잔액조회 에이전트

> 공통 결정(ADR-001~008)은 `docs/ADR.md`를 따른다.

### BAL-001: 조회 대상·의도 판단은 Python 코드, 문장 생성만 모델
**결정**: 계좌 매칭, 의도 판단(잔액·거래내역·일반 문의), 슬롯 값 생성은 코드로 한다. 모델은 슬롯 이름으로 상담 문장만 만든다.
**이유**: 원본 계좌번호와 금액이 모델에 닿지 않는다. 결과가 결정적이라 테스트하기 쉽다.
**트레이드오프**: 키워드 규칙이 놓치는 표현이 있을 수 있다. 자체 점검 셋에 넣어 보완한다.

### BAL-002: 출력 검증은 세 의도 모두 넓은 규칙으로, 실패하면 기본 문장으로 대체
**결정**: 잔액·거래내역·일반 문의(general) 응답 모두에 같은 규칙을 적용한다. 필수 슬롯 누락, 아라비아 숫자, `%`, 마스킹 토큰, 허용 밖 `{{슬롯}}`, 서류 키워드(서류·증명서·등본·재직·소득) 중 하나라도 있으면 그 의도의 기본 문장으로 대체한다. general의 기본 문장은 "해당 내용은 정확한 안내를 위해 상담원에게 확인해 주세요."이고, general은 허용 슬롯이 없다(세부 규칙은 ARCHITECTURE "출력 검증").
**이유**: 잔액 화면 인수 기준(모델은 `{{balance}}` 생성, 화면에 실제 금액)과 "지어낸 사실 0건"을 모델 품질과 상관없이 보장한다. 금액 형태의 숫자만 막으면 지어낸 기간·건수·금리를 놓친다. 슬롯이 없는 general 응답도 금리·서류 요건을 지어낼 수 있어 같은 규칙이 필요하다.
**LN-004와의 의도된 차이**: 대출 영역(LN-004)은 마스킹 토큰을 숫자 검사에서 빼고 "서류"라는 일반 단어를 허용한다. 잔액조회는 둘 다 대체한다. 잔액·거래내역 답변에는 마스킹 토큰이나 서류 안내가 필요한 경우가 없어서, 걸리면 지어냈거나 입력을 되풀이한 것으로 본다.
**트레이드오프**: "최근 5건"처럼 정상 문장도 대체되는 과대 대체를 감수한다. 대체 문장은 단조롭다. 대체 빈도를 로그로 보고 학습 데이터를 보강한다.

### BAL-003: 계좌가 여러 개면 선택지로 되묻는다
**결정**: 대상 계좌를 정하지 못하면 계좌 라벨 버튼을 보여준다(`choice: "balance"`). 되묻기 문구는 의도와 상관없이 "어느 계좌를 조회할까요?" 하나다. 입력한 계좌번호가 본인 계좌가 아니면 모델을 부르지 않고 "입력하신 계좌번호로 조회되는 계좌가 없습니다. 어느 계좌를 조회할까요?"와 본인 계좌 전체 선택지를 준다(계좌가 1개여도).
**이유**: 타이핑 없이 한 번 눌러 끝낸다(적은 프로세스). 문구가 하나면 잔액·거래내역 어느 질문에서 되물어도 어색하지 않다. 턴 상한 숫자는 아직 미정이다(`docs/PRD.md` 확인 필요 — 현재 설계 최대 봇 응답 3회, 2026-09-29 실측 J4도 3회).
**추가(2026-09-29, 3차)**: 되묻기 전에, 입력에 별칭이나 계좌번호 끝 4자리가 들어 있고 그런 본인 계좌가 하나뿐이면 그 계좌로 정한다. 되묻기 뒤 버튼 대신 "생활비 계좌 잔액 알려줘"를 치면 같은 되묻기가 반복되던 문제(PRD 사용자 여정 J9)를 푼다. 별칭·끝 4자리는 이미 선택지 라벨로 화면에 보이는 값이라 새로 노출되는 정보가 없다.
**트레이드오프**: 턴이 하나 늘어난다. 직접 입력은 새 질문으로 판단하므로 원래 질문의 의도(예: 거래내역)는 이어지지 않는다(ARCHITECTURE "알려진 한계" (d)).

### BAL-004: 일반 문의는 general 분기로 모델이 안내하고, 의도 판단을 계좌 결정보다 먼저 한다
**결정**: 의도는 balance / transactions / general 3분기다. 절차 표현(어디서·어떻게·방법·절차)이 있고 조회 요청 표현(알려·보여·얼마)이 없으면 general이다. 흐름은 라벨 클릭 확인 → 의도 판단 → general이면 계좌 결정·되묻기·슬롯 없이 모델 안내 / 아니면 계좌 결정 → 슬롯 → 출력 검증 순서다. general도 라벨 클릭 확인을 위해 `get_accounts`는 호출하지만, 모델 입력에는 계좌 정보를 넣지 않는다.
**이유**: 사용자 스토리 5가 이 영역의 약속이고, PM 고정 질문에 일반 문의가 섞이면 인수 때 걸린다. 계좌 결정이 먼저면 계좌 2개 고객(C002)의 일반 문의가 계좌 되묻기로 빠진다.
**트레이드오프**: 키워드 규칙이라 "잔액 알려주는 방법" 같은 표현은 조회로 판단된다. 자체 점검 셋으로 단어 목록을 늘린다.

### BAL-005: 순수 함수는 plain dict까지, handle()은 cherry-pick 발판 위에서 (2026-09-29 변경)
**결정**: mock API·계좌 결정·의도 판단·프롬프트 구성·출력 검증은 모델 없이 도는 순수 함수로 만든다. 계좌 결정 함수는 `AgentReply`가 아니라 plain dict(`{"account": ...}` 또는 `{"text": ..., "options": [...]}`)를 돌려주고, `AgentReply` 포장은 `BalanceAgent.handle()` 안에서만 한다. `handle()`과 `__init__.py` export는 팀원C의 스캐폴드·`llm`·`agents/base.py` 커밋(`a43c70a`·`e290476`·`6ed6cce`)을 `git cherry-pick -x`로 수정 없이 들여온 임시 발판 위에서 만든다. BAL-006 전처리 발판인 `app.masking.mask()`와 `training/common/split.py`도 원본 커밋(`6c61e00`·`925c7da`)을 같은 방식으로 가져온다. 발판은 팀원C의 feat-router가 main에 들어오면 그대로 대체된다.
**변경 사유(2026-09-29)**: 스텁이 main에 오기를 기다리면 `handle()` 흐름 테스트가 계속 밀려서, 임시 타입을 만들지 않고 팀원C 원본 커밋을 그대로 쓰는 방식으로 앞당겼다.
**이유**: 계약 3 타입은 팀원C 소유다. 로컬에 임시 타입을 만들면 스텁 병합 때 충돌하고 계약이 두 벌이 된다. 원본 커밋을 수정 없이 들여오면 계약은 한 벌이다.
**예외**: 발판 파일은 수정하지 않는다. 예외는 `app/agents/balance/__init__.py`(스텁 → 실제 export)와 `tests/router/test_base.py`(스텁 전용 검사에서 balance 제외) 둘뿐이다(ARCHITECTURE "알려진 한계").
**트레이드오프**: 발판 커밋 5개가 이 브랜치에 중복으로 들어온다. balance PR은 feat-router 스캐폴드가 main에 들어간 뒤 올리고, 병합 충돌은 위 예외 두 파일에서만 난다고 본다. PM 고정 질문 인수는 여전히 모델이 온 뒤로 밀린다.
**현황(2026-09-29)**: feat-router가 PR #4로 main에 들어갔다(`7466702`). 이제 main을 이 브랜치에 병합할 수 있다. `git merge-tree`로 미리 보면 충돌은 네 파일이다. 예외 두 파일 외에 BAL-006 커밋이 고친 `backend/README.md`와 `backend/training/requirements.txt`가 main의 변경과 겹친다. 예외 두 파일은 위 규칙대로 풀고, 나머지 둘은 양쪽 내용을 합친다.

### BAL-006: 잔액조회 데이터·학습·평가는 Mac에서 진행
**결정**: 잔액조회 영역만 Mac M4 Pro 24GB에서 데이터 전처리와 모델 학습·평가를 한다. Hugging Face의 팀 공통 Qwen Instruct 베이스를 로컬 MLX 형식으로 양자화하고, MLX LM의 LoRA 학습을 사용한다. 베이스는 팀원B(interest)와 같은 `Qwen/Qwen3-4B-Instruct-2507`이다(2026-09-29). 팀원C 벤치마크로 팀 공통 베이스가 달라지면 그 모델로 다시 학습한다. 추론·최종 품질 점검은 Ollama의 `cs-balance`로 수행한다. 나머지 영역의 Windows 학습 계획과 공통 `training/requirements.txt`는 유지한다.
**이유**: 이 영역 담당자의 현재 장비에서 학습을 진행할 수 있고, MLX LM은 Apple Silicon에서 양자화 베이스의 LoRA 학습을 지원한다. 원본 AI Hub 데이터와 학습 가중치는 Hugging Face에 올리지 않는다.
**트레이드오프**: MLX LM 자체 GGUF export는 Qwen 계열을 지원하지 않는다. 어댑터 병합·비양자화 결과의 llama.cpp GGUF 변환 호환성을 작은 실험으로 먼저 검증하고, 실패하면 모델 준비를 완료 처리하지 않는다. Mac의 24GB 통합 메모리와 최종 Windows 추론 기준을 모두 확인해야 한다. 명령과 검증 순서는 `backend/training/balance/MAC_TRAINING.md`에 둔다.
**마스킹 게이트**: 학습 데이터도 게이트웨이와 같은 `app.masking.mask()`를 반드시 사용한다(계약 4). import에 실패하면 전처리를 중단하며, 자체 정규식이나 fallback 마스킹으로 학습 데이터를 생성하지 않는다. main의 마스킹 또는 공통 분할 규칙이 바뀌면 balance 학습 데이터를 재생성한다.

### BAL-007: 모델 호출 실패는 게이트웨이 공통 처리에 맡긴다 (2026-09-29)
**결정**: `handle()`은 `llm.generate`의 `httpx.HTTPError`를 잡지 않는다. 게이트웨이가 잡아 세 에이전트 공통 문구("지금은 답변을 드릴 수 없습니다. 상담원 연결을 도와드릴까요?")로 답한다.
**이유**: 세 에이전트가 모델 장애에서 같은 모습을 보인다. 에이전트 코드에 예외 처리 분기가 늘지 않는다.
**검토한 대안**: 에이전트가 잡아 의도별 기본 문장과 슬롯으로 답하는 방식. 모델 없이도 잔액·거래내역을 보여줄 수 있지만 채택하지 않았다.
**트레이드오프**: `cs-balance`가 없거나 Ollama가 멈추면 슬롯 값이 준비돼 있어도 잔액·거래내역을 보여주지 못한다(PRD 사용자 여정 J12). 데모 전에 `cs-balance` 등록과 워밍업이 필요하다(`docs/frontend/ARCHITECTURE.md` "발표 전 체크리스트", main 기준). 되묻기·계좌 없음·본인 아님 턴은 모델을 부르지 않으므로 그대로 동작한다.

### BAL-008: 슬롯 응답은 템플릿 합성 샘플로 학습한다 (2026-09-29)
**결정**: `training/balance/prepare.py`는 AI Hub 샘플에 더해 잔액·거래내역 질문 변형 → `{{슬롯}}` 응답 변형의 합성 샘플을 만든다. 입력은 추론과 같은 `prompt.build_messages` 형식이고, 응답 템플릿은 그 의도의 출력 검증(`validate.is_valid`)을 통과해야 한다. AI Hub 샘플도 general 출력 검증을 통과한 `output`만 학습 정답으로 쓴다(팀원B INT-004와 같은 기준). 2026-09-29 로컬 집계로는 4,017건 중 `qa_topic` 불일치 373건을 빼고 2,037건이 통과한다.
**이유**: 로컬 잔액조회 QA 4,017건에 `{{슬롯}}` 응답이 0건이다. 슬롯 쓰는 법을 배우지 못하면 조회 턴 출력이 필수 슬롯 검사에 걸려 기본 문장으로만 나가고, 공통 인수 기준 6("모델은 `현재 잔액은 {{balance}}입니다`를 생성")을 채울 수 없다. 팀원B도 같은 문제로 합성 보강을 제안했다(feat-agent-interest의 INT-004).
**트레이드오프**: 합성 문장은 단조롭고, 비중이 크면 일반 문의 답변 톤이 흐려질 수 있다. 템플릿은 사람이 읽고 확인하며, 비중은 첫 소규모 학습 결과로 정한다. 출력 검증 필터로 AI Hub 샘플이 절반 가까이 줄어든다. 대신 추론 때 기본 문장으로 바뀔 문장(숫자·서류 안내 등)은 배우지 않는다.
