# ADR: 잔액조회 에이전트

> 공통 결정(ADR-001~008)은 `docs/ADR.md`를 따른다.

### BAL-001: 조회 대상·의도 판단은 Python 코드, 문장 생성만 모델
**결정**: 계좌 매칭, 의도 판단(잔액·거래내역·일반 문의), 슬롯 값 생성은 코드로 한다. 모델은 슬롯 이름으로 상담 문장만 만든다.
**이유**: 원본 계좌번호와 금액이 모델에 닿지 않는다. 결과가 결정적이라 테스트하기 쉽다.
**트레이드오프**: 키워드 규칙이 놓치는 표현이 있을 수 있다. 자체 점검 셋에 넣어 보완한다.

### BAL-002: 출력 검증은 세 의도 모두 넓은 규칙으로, 실패하면 기본 문장으로 대체
**결정**: 잔액·거래내역·일반 문의(general) 응답 모두에 같은 규칙을 적용한다. 필수 슬롯 누락, 아라비아 숫자, `%`, 마스킹 토큰, 허용 밖 `{{슬롯}}`, 서류 키워드(서류·증명서·등본·재직·소득) 중 하나라도 있으면 그 의도의 기본 문장으로 대체한다. general의 기본 문장은 "해당 내용은 정확한 안내를 위해 상담원에게 확인해 주세요."이고, general은 허용 슬롯이 없다(세부 규칙은 ARCHITECTURE "출력 검증").
**이유**: 잔액 화면 인수 기준(모델은 `{{balance}}` 생성, 화면에 실제 금액)과 "지어낸 사실 0건"을 모델 품질과 상관없이 보장한다. 금액 형태의 숫자만 막으면 지어낸 기간·건수·금리를 놓친다. 슬롯이 없는 general 응답도 금리·서류 요건을 지어낼 수 있어 같은 규칙이 필요하다.
**LN-004와의 의도된 차이**: 대출 영역(LN-004)은 마스킹 토큰을 숫자 검사에서 빼고 "서류"라는 일반 단어를 허용한다. 잔액조회는 둘 다 대체한다. 잔액·거래내역 답변에는 마스킹 토큰이나 서류 안내가 필요한 경우가 없어서, 걸리면 지어냈거나 입력을 되풀이한 것으로 본다.
**트레이드오프**: "최근 5건"처럼 정상 문장도 대체되는 과대 대체를 감수한다. 대체 문장은 단조롭다. 대체 빈도를 로그로 보고 학습 데이터를 보강한다.

### BAL-003: 계좌가 여러 개면 선택지로 되묻는다
**결정**: 대상 계좌를 정하지 못하면 계좌 라벨 버튼을 보여준다(`choice: "balance"`). 되묻기 문구는 의도와 상관없이 "어느 계좌를 조회할까요?" 하나다. 입력한 계좌번호가 본인 계좌가 아니면 모델을 부르지 않고 "입력하신 계좌번호로 조회되는 계좌가 없습니다. 어느 계좌를 조회할까요?"와 본인 계좌 전체 선택지를 준다(계좌가 1개여도).
**이유**: 타이핑 없이 한 번 눌러 끝낸다(적은 프로세스). 문구가 하나면 잔액·거래내역 어느 질문에서 되물어도 어색하지 않다. 턴 상한 숫자는 아직 미정이다(`docs/PRD.md` 확인 필요 — 현재 설계 최대 봇 응답 3회, 2026-09-29 실측 J4도 3회).
**추가(2026-09-29, 3차)**: 되묻기 전에, 입력에 별칭이나 계좌번호 끝 4자리가 들어 있고 그런 본인 계좌가 하나뿐이면 그 계좌로 정한다. 되묻기 뒤 버튼 대신 "생활비 계좌 잔액 알려줘"를 치면 같은 되묻기가 반복되던 문제(PRD 사용자 여정 J9)를 푼다. 별칭·끝 4자리는 이미 선택지 라벨로 화면에 보이는 값이라 새로 노출되는 정보가 없다.
**트레이드오프**: 턴이 하나 늘어난다. 직접 입력은 새 질문으로 판단하므로 원래 질문의 의도(예: 거래내역)는 이어지지 않는다(ARCHITECTURE "알려진 한계" (d)).

### BAL-004: 일반 문의는 general 분기로 모델이 안내하고, 의도 판단을 계좌 결정보다 먼저 한다
**결정**: 의도는 balance / transactions / general 3분기다. 절차 표현(어디서·어떻게·방법·절차)이 있고 조회 요청 표현(알려·보여·얼마)이 없으면 general이다. 흐름은 라벨 클릭 확인 → 의도 판단 → general이면 계좌 결정·되묻기·슬롯 없이 모델 안내 / 아니면 계좌 결정 → 슬롯 → 출력 검증 순서다. general도 라벨 클릭 확인을 위해 `get_accounts`는 호출하지만, 모델 입력에는 계좌 정보를 넣지 않는다.
**이유**: 사용자 스토리 5가 이 영역의 약속이고, PM 고정 질문에 일반 문의가 섞이면 인수 때 걸린다. 계좌 결정이 먼저면 계좌 2개 고객(C002)의 일반 문의가 계좌 되묻기로 빠진다.
**트레이드오프**: 키워드 규칙이라 "잔액 알려주는 방법" 같은 표현은 조회로 판단된다. 자체 점검 셋으로 단어 목록을 늘린다.

### BAL-005: 순수 함수는 plain dict까지, handle()은 cherry-pick 발판 위에서 (2026-09-29 변경)
**결정**: mock API·계좌 결정·의도 판단·프롬프트 구성·출력 검증은 모델 없이 도는 순수 함수로 만든다. 계좌 결정 함수는 `AgentReply`가 아니라 plain dict(`{"account": ...}` 또는 `{"text": ..., "options": [...]}`)를 돌려주고, `AgentReply` 포장은 `BalanceAgent.handle()` 안에서만 한다. `handle()`과 `__init__.py` export는 팀원C의 스캐폴드·`llm`·`agents/base.py` 커밋(`a43c70a`·`e290476`·`6ed6cce`)을 `git cherry-pick -x`로 수정 없이 들여온 임시 발판 위에서 만든다. BAL-006 전처리 발판인 `app.masking.mask()`와 `training/common/split.py`도 원본 커밋(`6c61e00`·`925c7da`)을 같은 방식으로 가져온다. 발판은 팀원C의 feat-router가 main에 들어오면 그대로 대체된다.
**변경 사유(2026-09-29)**: 스텁이 main에 오기를 기다리면 `handle()` 흐름 테스트가 계속 밀려서, 임시 타입을 만들지 않고 팀원C 원본 커밋을 그대로 쓰는 방식으로 앞당겼다.
**이유**: 계약 3 타입은 팀원C 소유다. 로컬에 임시 타입을 만들면 스텁 병합 때 충돌하고 계약이 두 벌이 된다. 원본 커밋을 수정 없이 들여오면 계약은 한 벌이다.
**예외**: 발판 파일은 수정하지 않는다. 예외는 `app/agents/balance/__init__.py`(스텁 → 실제 export)와 `tests/router/test_base.py`(스텁 전용 검사에서 balance 제외) 둘뿐이다(ARCHITECTURE "알려진 한계"). main 병합 때 `tests/gateway/test_api.py`(스텁 도달 검사를 loan으로 옮김)가 세 번째 예외로 더해진다(2026-09-29 결정).
**트레이드오프**: 발판 커밋 5개가 이 브랜치에 중복으로 들어온다. balance PR은 feat-router 스캐폴드가 main에 들어간 뒤 올리고, 병합 충돌은 위 예외 두 파일에서만 난다고 본다. PM 고정 질문 인수는 여전히 모델이 온 뒤로 밀린다.
**현황(2026-09-29)**: feat-router가 PR #4로 main에 들어갔다(`7466702`). 이제 main을 이 브랜치에 병합할 수 있다. `git merge-tree`로 미리 보면 충돌은 네 파일이다. 예외 두 파일 외에 BAL-006 커밋이 고친 `backend/README.md`와 `backend/training/requirements.txt`가 main의 변경과 겹친다. 예외 두 파일은 위 규칙대로 풀고, 나머지 둘은 양쪽 내용을 합친다.
**병합 시험 결과(2026-09-29, 커밋하지 않고 취소)**: 충돌은 이렇게 풀린다. `__init__.py`·`test_base.py`·`training/requirements.txt`는 이 브랜치 쪽을 쓴다(main 쪽 차이는 각각 스텁, `AREAS`의 balance, 주석 한 줄과 끝 줄바꿈뿐이다). `README.md`는 이 브랜치의 Mac 학습 안내 한 줄 뒤에 main의 구동 절차를 붙인다. 병합 뒤 전체 pytest는 1건이 실패했다(252 passed). 팀원C의 `tests/gateway/test_api.py::test_response_has_exactly_the_contract_fields`가 balance를 스텁으로 가정하고 "준비 중인 기능입니다."를 기대하기 때문이다. 실제 `handle()`은 모델을 부르므로 이 검사는 `test_base.py`와 같은 이유로 실패한다. 처리 방법은 PRD "구현 진행" 3차 계획 0을 따른다.

### BAL-006: 잔액조회 데이터·학습·평가는 Mac에서 진행
**결정**: 잔액조회 영역만 Mac M4 Pro 24GB에서 데이터 전처리와 모델 학습·평가를 한다. Hugging Face의 팀 공통 Qwen Instruct 베이스를 로컬 MLX 형식으로 양자화하고, MLX LM의 LoRA 학습을 사용한다. 베이스는 팀원B(interest)와 같은 `Qwen/Qwen3-4B-Instruct-2507`이다(2026-09-29). 팀원C 벤치마크로 팀 공통 베이스가 달라지면 그 모델로 다시 학습한다. 추론·최종 품질 점검은 Ollama의 `cs-balance`로 수행한다. 나머지 영역의 Windows 학습 계획과 공통 `training/requirements.txt`는 유지한다.
**이유**: 이 영역 담당자의 현재 장비에서 학습을 진행할 수 있고, MLX LM은 Apple Silicon에서 양자화 베이스의 LoRA 학습을 지원한다. 원본 AI Hub 데이터와 학습 가중치는 Hugging Face에 올리지 않는다.
**트레이드오프**: MLX LM 자체 GGUF export는 Qwen 계열을 지원하지 않는다. 어댑터 병합·비양자화 결과의 llama.cpp GGUF 변환 호환성을 작은 실험으로 먼저 검증하고, 실패하면 모델 준비를 완료 처리하지 않는다. Mac의 24GB 통합 메모리와 최종 Windows 추론 기준을 모두 확인해야 한다. 명령과 검증 순서는 `backend/training/balance/MAC_TRAINING.md`에 둔다.
**보강 (2026-09-30)**: 첫 학습 뒤 어댑터를 4bit 베이스가 아니라 16bit 원본 베이스(같은 리비전)에 병합해 GGUF로 만들었다(사용자 결정). 4bit 베이스에 `--dequantize`로 병합하면 4bit 반올림 오차가 남은 채로 Q4_K_M을 한 번 더 거친다. Q4_K_M이 일부 텐서를 6bit로 저장하는 이점도 살리지 못한다. 16bit 병합은 양자화를 한 번만 거치고, 팀원B(interest)의 내보내기 절차와도 같다. 최종 GGUF 크기(약 2.5GB)와 추론 속도는 두 방식이 같다. 트레이드오프: 어댑터는 4bit 베이스를 보며 학습했는데 16bit 베이스에 합치므로 조금 어긋난다(QLoRA의 일반적인 배포 방식이라 받아들인다). 병합할 때 메모리가 약 8~10GB 든다. 두 방식의 품질을 직접 비교하지는 않았다. 이 절차로 llama.cpp 변환과 `ollama create cs-balance`가 통과했다. 그래서 위 트레이드오프의 Mac 변환 게이트는 통과로 본다. 같은 GGUF의 Windows 로컬 추론 확인은 아직 하지 않았다.
**마스킹 게이트**: 학습 데이터도 게이트웨이와 같은 `app.masking.mask()`를 반드시 사용한다(계약 4). import에 실패하면 전처리를 중단하며, 자체 정규식이나 fallback 마스킹으로 학습 데이터를 생성하지 않는다. main의 마스킹 또는 공통 분할 규칙이 바뀌면 balance 학습 데이터를 재생성한다.

### BAL-007: 모델 호출 실패는 게이트웨이 공통 처리에 맡긴다 (2026-09-29)
**결정**: `handle()`은 `llm.generate`의 `httpx.HTTPError`를 잡지 않는다. 게이트웨이가 잡아 세 에이전트 공통 문구("지금은 답변을 드릴 수 없습니다. 상담원 연결을 도와드릴까요?")로 답한다.
**이유**: 세 에이전트가 모델 장애에서 같은 모습을 보인다. 에이전트 코드에 예외 처리 분기가 늘지 않는다.
**검토한 대안**: 에이전트가 잡아 의도별 기본 문장과 슬롯으로 답하는 방식. 모델 없이도 잔액·거래내역을 보여줄 수 있지만 채택하지 않았다.
**트레이드오프**: `cs-balance`가 없거나 Ollama가 멈추면 슬롯 값이 준비돼 있어도 잔액·거래내역을 보여주지 못한다(PRD 사용자 여정 J12). 데모 전에 `cs-balance` 등록과 워밍업이 필요하다(`docs/frontend/ARCHITECTURE.md` "발표 전 체크리스트", main 기준). 되묻기·계좌 없음·본인 아님 턴은 모델을 부르지 않으므로 그대로 동작한다.

### BAL-008: 슬롯 응답은 템플릿 합성 샘플로 학습한다 (2026-09-29)
**결정**(AI Hub 샘플 처리는 BAL-010에서 바뀜): `training/balance/prepare.py`는 AI Hub 샘플에 더해 잔액·거래내역 질문 변형 → `{{슬롯}}` 응답 변형의 합성 샘플을 만든다. 입력은 추론과 같은 `prompt.build_messages` 형식이고, 응답 템플릿은 그 의도의 출력 검증(`validate.is_valid`)을 통과해야 한다. AI Hub 샘플도 general 출력 검증을 통과한 `output`만 학습 정답으로 쓴다(팀원B INT-004와 같은 기준). 2026-09-29 로컬 집계로는 4,017건 중 `qa_topic` 불일치 373건을 빼고 2,037건이 통과한다.
**이유**: 로컬 잔액조회 QA 4,017건에 `{{슬롯}}` 응답이 0건이다. 슬롯 쓰는 법을 배우지 못하면 조회 턴 출력이 필수 슬롯 검사에 걸려 기본 문장으로만 나가고, 공통 인수 기준 6("모델은 `현재 잔액은 {{balance}}입니다`를 생성")을 채울 수 없다. 팀원B도 같은 문제로 합성 보강을 제안했다(feat-agent-interest의 INT-004).
**트레이드오프**: 합성 문장은 단조롭고, 비중이 크면 일반 문의 답변 톤이 흐려질 수 있다. 템플릿은 사람이 읽고 확인하며, 비중은 첫 소규모 학습 결과로 정한다. 출력 검증 필터로 AI Hub 샘플이 절반 가까이 줄어든다. 대신 추론 때 기본 문장으로 바뀔 문장(숫자·서류 안내 등)은 배우지 않는다.

### BAL-009: 콜센터식 정답은 학습에서 뺀다 (2026-09-29)
**결정**: `prepare.py`는 AI Hub `output`이 다음 둘 중 하나면 학습 정답에서 뺀다. 규칙과 예문은 ARCHITECTURE "학습 데이터"가 기준이다. ① 고객에게 성함·생년월일·계좌번호·비밀번호·주민번호·카드번호를 알려 달라거나 입력해 달라고 요구한다. ② 챗봇이 할 수 없는 발송·전송·발급·정정·조치·처리를 "~해 드리겠습니다/드리니"로 약속한다. 상담원·담당 부서 "연결" 안내와 고객센터 문의 안내는 남긴다. 기본 문장("상담원 연결을 도와드릴까요?")과 같은 방향이기 때문이다.
**이유**: train-export step의 valid 점검(2026-09-29, 20건 판독 + 전체 집계)에서 원천이 콜센터 상담원 답변이라 챗봇이 하면 안 되는 행동이 섞여 있음을 확인했다. valid AI Hub 139건 중 개인정보 요구가 21건, 행동 약속이 9건이다. 런타임 출력 검증(BAL-002)은 숫자·`%`·마스킹 토큰·서류 단어만 보므로 이런 문장은 화면까지 나간다. 학습은 `--mask-prompt`라 loss가 마지막 assistant 답에만 걸리므로 `output`만 거르면 된다. 행동은 GGUF 변환·Ollama 등록까지 가야 보이므로 학습 전에 막는 편이 싸다.
**트레이드오프**: 정규식이라 오탐이 있다(예: "앱에서 수취인 계좌번호를 입력해 주세요"). 이런 문장도 절차를 지어낸 안내라 빠져도 손해가 작다. AI Hub 통과분은 2,327건 → 약 2,046건(train 2,029 → 1,805)으로 준다. "조회 결과 단정"(예: "정상적으로 처리되었습니다", train 약 21%)은 오탐이 많고 줄어드는 양이 커서 거르지 않는다. system prompt와 자체 점검 Q8로 확인한다(→ BAL-010에서 제외로 바꿈).
**보강 (2026-09-29)**: 1차 규칙으로 가공본을 다시 만들고 valid 22건을 읽었다. 동사·어미 목록 밖 표현 8건이 남아 있었다. 행동 약속이 7건("진행해·전달해·제공해 드리겠습니다", "처리해 드립니다", "즉시 진행하겠습니다", "발송해·정리해 드릴 수")이고, 개인정보 요구가 1건("제공해 주셔야")이다. 사용자 결정으로 행동 약속의 동사·어미를 넓혔다. `조회해 드리겠`도 넣었다. general 턴의 모델은 조회를 할 수 없기 때문이다. 개인정보 요구에는 `제공해`를 더했다. `드릴 수 없`은 할 수 없다는 안내라 남긴다. 서류·양식 단어(계약서·양식·신청서)는 더하지 않았다. `확인해 드리겠습니다`(train 28건 남음)도 규칙에 넣지 않았다. AI Hub 통과분은 2,048건 → 1,831건(train 1,807 → 1,626)으로 준다. 규칙과 예문은 ARCHITECTURE "학습 데이터"가 기준이다.

### BAL-010: AI Hub 답변은 LLM으로 챗봇 답변으로 다시 써서 학습한다 (2026-09-29)
**결정**: `training/balance/rewrite.py`가 AI Hub QA마다 `answer`와 `output`을 한 번의 호출로 다시 쓴다. 입력은 마스킹을 거친 네 필드이고, 모델은 Claude Haiku 4.5(`claude-haiku-4-5`)다. API 키 대신 Claude Code 헤드리스 모드(`claude -p`, 사용자 구독 로그인)로 돌린다. 호출 한 번에 QA 20건을 묶고 `--json-schema`로 구조화 출력을 받는다. 결과는 로컬 캐시(`data/processed/balance/rewrites.jsonl`, gitignore)에 쌓고, `prepare.py`는 이 캐시만 읽어 결정적으로 가공한다. 재작성 규칙은 ARCHITECTURE "학습 데이터 → LLM 재작성"이 기준이다. 요점은 존댓말 200자 이내, 조회 결과 단정·행동 약속·개인정보 요구·지어낸 사실 금지, 원래 답의 일반 안내 유지다. 다시 쓴 답에도 결정적 필터(`is_valid`·상품명·BAL-009·조회 단정·비식별 표시·200자)를 안전망으로 적용한다. 같은 결정에 다음도 포함한다.
- 첫 턴 샘플: 다시 쓴 `answer`로 history 없는 `[question] → answer` 샘플을 더한다. 이어진 턴 샘플의 history에도 다시 쓴 `answer`를 쓴다(BAL-008의 "AI Hub는 `output`만"을 바꾼다).
- 조회 결과 단정은 이제 뺀다(BAL-009의 "거르지 않는다"를 바꾼다). AI Hub 비식별 표시(`★`·`●`·`○`·`OO`)가 남은 정답도 뺀다.
- 합성 보강: general 의도 "상담원 안내" 샘플과, mock 가상 계좌번호를 넣어 `mask()`로 `[계좌번호_1]` 토큰을 만든 잔액·거래내역 질문 샘플을 더한다.

**이유**: 가공본을 점검한 결과(2026-09-29), 필터 방식에는 한계가 있었다. 콜센터 정답의 17%가 조회 결과를 단정했고, 6%에 비식별 표시가 남았다. 메뉴·절차를 지어낸 문장은 정규식으로 셀 수조차 없었다. AI Hub 샘플이 모두 "상담원 장문 답 뒤 이어진 질문" 모양이라 자체 점검 Q6~Q8 같은 첫 턴 general 질문도 학습 데이터에 없었다. 원천 입력의 42%에는 런타임에 나오지 않는 `★★`·`OO` 표시가 있다. 반대로 런타임 토큰 `[계좌번호_1]`이 든 입력은 4건뿐이었다. 다시 쓰면 필터로 버리던 데이터를 살리면서 에이전트가 할 일(조회는 코드, 모델은 안내)에 맞는 답을 배운다. "데이터셋 이용조건: 제3자 제공 금지"는 잘못된 정보라고 사용자가 정정했다. `docs/PRD.md`의 "국외 클라우드 학습 금지"는 학습에만 적용하고, 데이터 가공에는 외부 API를 써도 된다(사용자 결정). 모델은 사용자가 제시한 저가 후보(Claude Haiku 4.5, gpt-5-mini, gpt-4o-mini, gpt-4.1-mini) 중에서 골랐다. gpt-4o-mini·gpt-4.1-mini는 미묘한 금지 규칙을 지키는 힘이 약해 뺐다. gpt-5-mini와는 비용 차이가 몇 달러라 작다. 그래서 구조화 출력을 검증된 문서로 구현할 수 있는 Haiku 4.5를 골랐다. 같은 날 사용자 결정으로 API 대신 Claude Code로 돌리게 되었다. 그래서 API 키와 별도 과금이 필요 없고, 모델은 Claude 계열 중에서 `--model`로 고른다.
**트레이드오프**: 구독 사용량을 쓴다(호출 약 207번, `total_cost_usd`는 참고값으로 기록한다). 배치 API보다 느리므로 `--jobs`로 몇 개를 병렬로 돌린다. `--bare` 모드는 API 키만 받아서 쓸 수 없다. 그래서 사용자 전역 CLAUDE.md는 읽히지만, 빈 임시 폴더에서 실행해 프로젝트 CLAUDE.md는 읽히지 않게 한다. 결과가 매번 달라서 캐시가 필수다. 캐시가 없는 기기에서는 AI Hub 샘플이 0건이 된다. 모델이 규칙을 어길 수 있으므로 전체 실행 전에 30건 시범과 사람 판독을 거친다. 위반이 많으면 규칙이나 모델을 바꾼다. 학습 데이터 말투가 재작성 모델을 닮는다. 학습용 외부 호출이라 `app/llm`의 `generate()` 규칙(런타임 모델 호출 한 곳)과는 별개다. 마스킹을 거친 텍스트만 보낸다(계약 4와 같은 이유).
**보강 (2026-09-29)**: train-export step에서 `rewrite --limit 30` 시범을 돌렸다. Haiku 4.5로 3분 33초 걸렸고, `total_cost_usd`는 0.1488, 누락은 0건이었다. 숫자·가림 표시·200자·조회 결과 단정·개인정보 요구 규칙은 모두 지켰다. 그러나 QA 11개에서 답 약 14개(60개 중 약 22%)에 문제가 남았다. 원문의 검증되지 않은 사실을 옮긴 답이 약 9개였다("수수료는 발생하지 않습니다", "휴일이면 전 영업일에 처리", 한 고객의 조회 결과를 일반 정의로 바꾼 지급정지 설명 등). 메뉴 이름이 2개, 나중에 해 줄 일을 약속한 답이 2개, 같은 묶음의 다른 item 내용이 섞인 답이 1개였다. 모델은 규칙 7의 "지어내지 않는다"를 "새로 만들지 않는다"로 읽었다. 그래서 원문에 있던 사실을 일반 안내(규칙 10)로 보고 살렸다. 사용자 결정으로 모델과 묶음 크기는 그대로 두고 규칙만 보강했다. 5에는 나중에 해 줄 일 약속 금지를, 7에는 원문 사실도 옮기지 않는다는 것과 조회 결과를 일반 설명으로 바꾸지 않는다는 것을 더했다. 10에는 일반 안내의 범위를 적고, 11(item끼리 내용 섞지 않기)을 새로 만들었다. 트레이드오프: 답이 더 자주 상담원 안내로 끝난다. 시범에서도 60개 중 49개가 상담원·고객센터 안내를 담았다. 캐시 키에는 규칙이 들어가지 않는다. 그래서 기존 캐시 30건은 사람이 옮기고 시범부터 다시 한다. 결정적 안전망 필터는 이번에 바꾸지 않고, 재시범 결과를 보고 정한다.
**결과 (2026-09-30)**: 보강한 규칙으로 같은 30건을 다시 돌렸다. 5분 51초 걸렸고, `total_cost_usd`는 0.2306, 누락은 0건이었다. 1차에서 나온 위반(수수료·휴일 처리·규정 변경·자동 해제 단정, 나중에 해 줄 일 약속, item 섞임)은 사라졌다. 문제가 남은 답은 60개 중 약 6~8개로, 원문의 앱 기능 주장과 신분증 같은 준비물이었다. 상담원·고객센터 안내는 49개에서 42개로 줄었다. 사용자 결정으로 이 규칙 그대로 전체를 돌렸다(`--jobs 4`, 2시간 13분). 누락 16건은 한 번 더 실행해 채웠다. 캐시는 4,137건이고 `total_cost_usd` 합은 22.93이다. 결정적 안전망 필터는 바꾸지 않았다. prepare에서 필터에 걸려 빠진 샘플은 세 분할을 합쳐 첫 턴 118개, 이어진 턴 99개다. valid 24건을 판독한 결과 개인정보·슬롯·존댓말·조회 결과 단정 기준은 모두 통과했다. 대신 "확인해 드리겠습니다" 약속(BAL-009 보강 때 규칙에 넣지 않은 표현, train 목표의 0.5%)과 원문식 사실 주장이 조금 남았다. 사용자 결정으로 그대로 학습했고, 자체 점검 step에서 모델 동작으로 확인한다.
