# ADR: 대출문의 에이전트

> 공통 결정(ADR-001~008)은 `docs/ADR.md`를 따른다.

### LN-001: 금액이 아닌 대출 정보는 프롬프트에 넣는다
**결정**: 만기일, 연장 가능 여부, 대출 종류(일반 명칭)는 프롬프트에 텍스트로 넣는다. 남은 원금은 슬롯으로만 전달한다.
**이유**: 마스킹 필수 항목은 금액이다(PRD). 날짜·여부는 모델이 문장 속에서 자연스럽게 쓰는 편이 품질이 좋다.
**트레이드오프**: 날짜가 모델 입력 로그에 남는다. 개인정보 필수 마스킹 항목이 아니므로 허용한다.

### LN-002: 금리·서류 요건은 답하지 않고 상담원 확인을 안내한다
**결정**: mock 데이터에 금리를 두지 않는다. 출력에 퍼센트 수치가 있으면 기본 문장으로 대체한다. 서류 요건은 학습 데이터의 일반 안내를 넘으면 상담원 확인을 안내하도록 시스템 프롬프트에 명시한다.
**이유**: 지어낸 금리·서류 요건이 1건이라도 나오면 즉시 인수 불합격이다.
**트레이드오프**: "연장하려면 뭐가 필요해요?"에 대한 답이 덜 구체적일 수 있다.

### LN-003: 대출이 없으면 모델을 호출하지 않는다
**결정**: 조회 결과가 없으면 고정 문장을 돌려준다.
**이유**: 모델이 없는 대출을 지어낼 여지를 없앤다. 응답도 빨라진다.
**트레이드오프**: 없음 안내 문장이 단조롭다.

### LN-004: 출력 검증은 허용 목록 방식이다
**결정**: 출력에서 프롬프트에 준 만기일 표기와 마스킹 토큰(계약 4)만 숫자로 허용하고, 그 밖의 아라비아 숫자·허용 밖 슬롯·구체적인 서류명 키워드가 있으면 기본 문장으로 대체한다. 연장 불가인데 같은 문장 안에 부정 표현 없이 "가능"이라고 답한 경우도 대체한다(세부 규칙은 ARCHITECTURE handle() 6단계). 드라이런 질문에 대한 결정(2026-09-28):
- 서류: "서류"라는 일반 단어는 막지 않고 구체적인 서류명(증명서·등본·재직·소득 등)만 막는다. LN-002가 일반 안내("필요한 서류는 상담원에게 확인해 주세요")를 허용하기 때문이다.
- 마스킹 토큰: `[금액_1]` 같은 토큰은 원본 값이 아니므로 숫자 검사에서 제외한다. 토큰 뒤에 붙은 다른 숫자는 그대로 걸린다.
- 부정 표현: 문장 단위로 판정한다. 다른 문장의 "않"·"없"이 "연장이 가능합니다"를 통과시키면 안 되기 때문이다.
- 없는 채널(2026-09-29 추가, `CHANNEL_KEYWORDS`): 앱·어플·모바일·뱅킹·홈페이지·웹사이트·콜센터·고객센터·영업점이 있으면 대체한다. 우리 서비스에 없는 경로를 안내하면 고객이 존재하지 않는 곳을 찾게 된다. 고객센터를 없는 채널로 볼지는 팀 확인이 필요하다(v1 응답 70건 중 3건이 이 키워드 때문에만 걸렸다).
- 못 지키는 약속(2026-09-29 추가, `PROMISE_PATTERNS`): "확인 후"·"안내/알려/처리/연결/보내 드리겠"·"조회해 보겠"·"잠시만 기다려"·"문자로"가 있으면 대체한다. 챗봇은 후속 안내나 발송을 할 수 없다.
- 서류명 보강(2026-09-29): 명세서·등기부·계약서·증빙을 `DOCUMENT_KEYWORDS`에 더했다. v1 모델이 실제로 지어낸 서류명이다.
**이유**: "금액 형태의 숫자" 같은 금지 목록은 만기일(`2027-03-31`)과 구분이 안 되고, 지어낸 기간·날짜("3영업일", "2027-04-01")를 놓친다. 지어낸 사실 1건이 즉시 불합격이므로 놓치는 쪽보다 과하게 대체하는 쪽이 낫다.
**트레이드오프**: 정상 답변도 숫자가 하나라도 섞이면 기본 문장으로 대체될 수 있어 답변이 단조로워진다. 서류명 키워드 목록과 부정 표현 판별은 휴리스틱이라 완전하지 않다. "서류를 제출하셔야 합니다"처럼 서류명 없이 요건을 지어내는 문장은 걸리지 않는다. 모델이 마스킹 토큰을 되풀이하면 화면에 토큰이 그대로 보일 수 있다(치환은 게이트웨이 소관). 그래서 인수 전 PM 고정 질문으로 확인한다. 2026-09-29 추가 규칙은 정상 답변도 대체할 수 있다("최종 결과는 고객센터로 확인해 주셔야 합니다" 같은 상담원 안내가 대체된다). 서류·조건 외의 사실 주장("일부만 먼저 상환하실 수 있습니다" 등)은 키워드로 잡지 못한다. 근거 수치: v1 모델 응답 70건 중 이전 검증기는 4건, 새 검증기는 22건을 대체했다. 이 70건은 규칙을 만들 때 본 응답이라 22건은 낙관적인 숫자다. 수동 시드 118건은 새 검증기에서 0건 막혔다.

### LN-005: 만기·연장·조회 의도는 코드가 나누지 않는다
**결정**: 잔액조회 에이전트와 달리 의도 분기 코드를 두지 않는다. 대출 종류·만기일·연장 가능 여부와 슬롯 2개를 항상 프롬프트에 주고, 모델이 질문에 맞는 부분을 답한다.
**이유**: 슬롯이 의도와 무관하게 항상 같아서 분기할 이유가 없다. 분기 코드를 두면 키워드 누락 버그만 늘어난다.
**트레이드오프**: 질문과 무관한 정보(예: 만기 문의에 원금)가 섞일 수 있다. 존댓말 상담 톤·주제 적합 기준에는 영향이 없다고 본다.

### LN-006: 프롬프트 구성과 날짜 표기
**결정**: "대출 정보"·"사용할 수 있는 슬롯" 줄은 별도 메시지가 아니라 마지막 user 메시지에 `masked_text` 뒤로 붙인다. 시스템 프롬프트의 원본은 `prompt.py`의 `SYSTEM_PROMPT` 하나이고, Modelfile에 같은 문구를 복제하지 않는다. 프롬프트와 기본 문장의 만기일은 `YYYY-MM-DD`(예: `2027-03-31`)로 쓴다. 검증기는 `YYYY년 M월 D일` 표기도 허용한다.
**이유**: 학습 데이터도 user 발화 하나에 질문이 담기는 구조라 추론 입력과 맞추기 쉽다. 시스템 프롬프트를 두 곳에 두면 문구가 어긋난다. ISO 표기는 형식이 하나라 검증이 단순하다.
**트레이드오프**: 학습 때는 이 줄들이 없으므로 학습 대화 구성 때 같은 형식으로 붙여야 한다(step 3). 모델을 1개로 합쳐 영역별 `SYSTEM`이 필요해지면(공통 계약 5, 팀 합의 대기) 그때 문구를 한 곳으로 옮긴다.

### LN-007: v2 학습 데이터는 AI Hub 답변을 쓰지 않는다 (2026-09-29)
**결정**: AI Hub는 질문 공급원으로만 쓰고, 정답은 우리가 정한 문장으로 붙인다(`prepare.py --mode replace`). 구성은 수동 시드(만기·원금·연장·연장 불가 사유·거절 유형, ×3 복제)와 교체 샘플이다. 교체 샘플은 질문이 "연장 서류·조건" 또는 "금리" 한 유형에만 해당할 때 만들며, 정답은 상담원 안내 문장 6종(조사는 받침에 맞춰 붙임)에 일부만 마무리 문장을 붙인다. 유형별 상한은 서류·조건 125, 금리 126이다. 질문 첫 턴만 쓰는 단일 턴이라 상담사의 이전 답변이 학습 정답으로 새어 들어가지 않는다.
**제외**: 수수료(v2 결과를 보고 추가 여부 결정), 이자·상환·납부·연체(이자/연체 에이전트 담당), 익명화 기호가 든 질문, 두 유형에 모두 해당하는 질문.
**이유**: v1 학습 데이터의 상담사 답변을 점검했더니(30건) 안전한 것이 없었다. 우리 서비스에 없는 앱·지점·ARS 절차, 못 지키는 약속, 지어낸 서류·금리를 그대로 말한다. v1 모델도 서류·금리·수수료·상환 질문에서 같은 식으로 지어냈다(70건 중 16건).
**트레이드오프**: 학습 행이 2,745에서 약 740으로 줄고 상담사 말투를 거의 배우지 못한다. AI Hub의 마무리 문장 4종을 일부 답변에 붙여 보완한다. 질문 유형 판별은 키워드라 오분류가 남을 수 있다. 검증셋(`loan_val_replace.jsonl`)에는 슬롯 답변이 없어 eval loss는 거절 유형만 반영한다. 학습 대상 주제 판별은 여전히 `qa_topic`이며 기준 통일(`consulting_topic`)은 팀 합의 대상이다.

### LN-008: v3 수동 시드 확장 — 약점 보강과 문형 조합 (2026-09-29)
**결정**: 수동 시드를 164건에서 350건으로 늘린다(train 298건 + 질문 단위로 뗀 val 52건). 학습 설정(lr 2e-4, epoch 3, LoRA r=16)과 교체 샘플(서류·조건 125, 금리 126)은 v2와 같다. 추가한 것은 ① 두 가지 이상을 함께 묻는 복합 질문, ② 만기·원금·연장 여부를 모두 답하는 전반 조회, ③ 비용·수수료·위약금·페널티 질문(질문의 주제어로 답하고, 연장 관련이면 연장 여부를 먼저 답한 뒤 나머지를 상담원에게 넘김), ④ 이전 턴을 잇는 맥락 시드 12건, ⑤ 기본 질문(만기·원금·연장)의 답변 문형 다양화, ⑥ 말투 변형 28건(반말·명사형 짧은 질문·오타), ⑦ 마스킹 토큰이 든 질문 16건(토큰을 되풀이하거나 값을 맞다/틀리다 하지 않음), ⑧ 구체적인 서류명·숫자가 든 서류·조건·금리 질문 17건(v2는 0건; 되풀이·확인하지 않고 상담원에게 넘김)이다. "네,"는 예/아니오 질문에 긍정(연장 가능)으로 답할 때만 붙인다. 본문 문형은 사실(만기·원금·연장 여부)마다 9~12가지, 회피 문형은 7가지를 직접 썼고 AI Hub 문구를 쓰지 않았다. 도입·맺음 문구는 약 1/3에만 붙이고 상담원 안내가 이미 들어간 답에는 맺음을 붙이지 않는다(안내가 두 번 나오는 것을 막음). 만기일은 mock 2개(시드의 약 41%) 외에 실재하는 날짜 41개를 고정 seed로 생성해 쓴다. mock 날짜 두 개만 학습하면 모델이 프롬프트의 날짜를 복사하지 않고 외울 위험이 있다. 날짜 표기는 ISO 그대로 둔다(LN-006). 날짜 뒤에 조사(로/으로)가 필요한 문형은 쓰지 않는다(날짜 끝소리에 따라 틀린다).
**이유**: v2 Golden Set 57문항 평가에서 검증기 통과 57/57이었지만 ① 연장 여부와 원금을 함께 물으면 원금을 빠뜨린 답이 검증기를 통과했고(R06), ② 연장 수수료 질문에 "금리"로 답했으며(F09), ③ 대출 전반을 물으면 아는 정보도 회피했고(C28), ④ 답변 문형이 6개 반복이라 고유 답변 66개·평균 57자로 딱딱했다. 원인이 시드 부족(복합 4·수수료 5·전반 2·맥락 0)과 문형 반복으로 추정된다.
**검증**: 새 시드는 검증기·정제 규칙을 모두 통과해야 하고(`tests/loan/test_manual_seed_v3.py`), 물어본 항목이 답에서 빠지면 안 된다. 개선 효과는 시드와 겹치지 않는 새 문항 20건(`golden_set_v3.jsonl`)과 기존 Golden Set(회귀)으로 잰다.
**트레이드오프**: 원인은 추정이다. 여러 변경을 한 번에 넣어서 어느 것이 효과를 냈는지 분리하지 못한다. 문형 조합이라 표현은 늘지만 여전히 우리가 쓴 문장 안이다. 복합·전반 조회 답변은 화면에 보이는 "조회"를 한 번만 쓴다(`{{extendable_status}}`가 "…조회됩니다"로 치환되므로 그 슬롯이 있으면 모델 문장은 쓰지 않는다). val은 prepare가 수동 시드 중 질문 단위로 뗀 행(전체 질문의 15%)을 복제 없이 1배로 넣는다 — 이전에는 val에 슬롯 답변이 없어 eval loss가 거절 유형만 반영했다. 실측: 문형(날짜·슬롯을 지운 답) 55 → 247종, 평균 길이 57 → 68자, 시드에 쓰인 날짜 43종. 도입·맺음을 줄인 만큼 길이가 줄었다(문형 다양화와 맞바꿈). 고유 답변 기준은 목표 250을 못 채워 230으로 두었다(사유·추측·요청은 `test_prepare`가 문형 상한을 둔 기존 유형). 기존 `test_prepare.py`의 두 검사(모든 시드의 `answer` 비어 있음, 연장 답변 문형 4개 이하)는 맥락 시드와 문형 다양화에 맞춰 완화했다(연장 문형 상한 40).
**기준선(v3)**: v3 학습(`outputs_v3`, 어댑터 기준 eval_loss 0.085, 216스텝, 2,222초)에 쓴 파일의 sha256이다. 이후 시드를 고치더라도 이 파일은 덮어쓰지 않고 새 이름(v4 등)으로 만든다. `data/`는 gitignore라 해시만 남긴다.
