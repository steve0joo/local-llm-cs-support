# 모델 평가: cs-loan (팀 공용틀 적용)

팀 공용틀(`EVALUATION_공용틀.md`)을 대출문의 에이전트에 적용한 평가 문서다. 도구는 `backend/training/loan/evaluate.py`, 테스트는 `backend/tests/loan/test_evaluate.py`다. 이 문서는 **결과를 보기 전에 기준을 적어 둔 것**이고, 평가 뒤에는 기준을 바꾸지 않는다(바꾸면 사후 변경이라고 표시한다). 결과는 9절에 채운다.

- 이 문서는 팀 기준(공용틀)이다. v4 개발 중 자체 기준은 `EVAL_CRITERIA_v3.md`, `EVAL_CRITERIA_v4.md`, 결과는 `EVAL_RESULT_v4.md`에 그대로 두고, 자체 평가 결과를 공식 결과로 옮겨 쓰지 않는다.
- 대상: **Base, v3, v4**가 본 평가 대상이다(수동 판정·Judge). 사람 평가는 최종 후보 v4와 Base만 했다(9-6절). **v1(`cs-loan-test`)과 v2는 온도 0 자동 채점만** 돌려 버전 비교표(12-4)에 넣고 수동 판정은 하지 않는다. v5는 만들지 않고 학습도 하지 않는다.

## 1. 채택 판단

> Base보다 상담 규칙 준수가 좋아졌고, 기존 능력과 조회값 활용은 손상되지 않았으며, 사람이 보아도 쓸 만한가?

세 항목에 모두 "예"일 때만 튜닝 모델을 채택한다. 아니면 Base(또는 이전 채택 모델)를 유지한다. loss는 학습이 진행됐다는 신호일 뿐이다. 이 프로젝트에서도 v2~v4 모두 val loss는 낮았지만 행동 결함(거절 문형 뒤집힘, 조건 슬롯 누락, 일본어 혼입)은 평가에서 드러났다.

- **M05와 K10은 같은 유형(수수료)** 이라 거의 같은 질문이다. 결과 표에서는 유형별 표에 `K10+M05`로 묶어 표시하고, 판정 점수에서는 두 문항이 각각 센다(같은 유형이 두 번 반영됨).

- **회귀 20문항 중 2문항(R07, R08)은 대출 없는 고객(C001)** 이다. 서비스(`agent.py`)는 이 경우 모델을 부르지 않고 고정 문장을 돌려주므로 평가도 모델을 부르지 않고(`bypass`) 모든 모델이 같게 통과한다. 이 2문항을 빼면 18문항이 되어 1문항이 5.6%p라서 "5%p 이내"가 "하락 0"이 된다. 공용틀의 20문항(1문항 = 5%p) 기준을 지키려고 남긴다. 그래서 실제로 모델 차이를 보는 것은 18문항이고, 결과 표에는 **20문항 결과와 모델 호출 18문항 결과를 함께 적는다**.
- 최종 확인용은 `golden_set.jsonl`의 옛 `final` 10문항이 아니라 `golden_set_final_v4.jsonl`이다(`EVAL_CRITERIA_v4.md` 2절에서 이미 최종 확인용으로 확정). 옛 `final`은 평가에 쓰지 않는다. 두 파일 모두 문항 ID가 F01~F10이라 헷갈리기 쉽다.
- **한계(숨기지 않는다)**
  - regress는 v3·v4 자체 평가에서 이미 "dev"로 돌린 문항이다(문항 자체는 학습에 쓰지 않았고 시드와 겹치지 않는다). 회귀는 Base와의 차이만 보므로 영향이 상대적으로 작지만 "처음 보는 문항"은 아니다.
  - K20은 v4 시드를 고정한 뒤 v4 응답을 보기 전에 쓴 문항이라 v2·v3 설계에는 쓰이지 않았지만, **v3·v4 자체 평가에서 응답을 본 적이 있다**(K06 등). v4에 대해서는 완전히 처음 보는 문항이 아니다. 완전히 새로운 것은 M01~M10뿐이다.
  - final(F01~F10)은 v4 자체 평가에서 v3·v4로 이미 한 번 돌렸다. 공용틀 12-3의 "마지막에 한 번만"은 이미 지켜지지 않았다. 시드 설계에는 쓰지 않았고(겹침 검사만) v5를 만들지 않으므로 문항에 맞춰 모델을 고치는 일은 없지만, 이 점을 결과 해석에 명시한다.
  - 문항이 적다(30, 20, 10). 1문항이 각각 3.3%p, 5%p, 10%p이므로 작은 차이는 우연일 수 있다.

## 4. 채점 (자동, API 없이)

모델 원문(`answer`, **raw**)을 채점한다. 서비스에서 검증기가 막아 대체 문장(`served`, **final**)으로 바뀌는 경우도 모델은 실패로 센다. 결과에는 **raw와 final 둘 다** 적는다(final = 검증기 적용 후 서비스가 보여 주는 답을 같은 기준으로 채점). 검증기는 일본어·한자 차단 패치가 들어간 현재 버전이다.

- **성공(rule)** = 검증기 통과(`validate.is_valid_output`, 일본어·한자 차단 포함) **그리고** 그 문항의 필수 코드를 모두 충족.
- 필수 코드: 문항에 `must`가 있으면 그것(compare의 K·M, final). 없으면(compare, regress) `expect`에서 옮긴 코드 + `polite` + `no_fabrication`(+ 카테고리가 수수료면 `topic_fee_word`).
  - `expect` → 코드: `date`(만기일이 정확히 하나, 다른 날짜 없음), `slot_principal`, `slot_extend`, `refer`(상담원 안내). `off_topic`·`no_loan`은 추가 코드가 없다(존댓말·지어내지 않음만).
- 추가 코드(M08): `no_affirm` = "네,"로 시작하는 문장이나 "맞습니다·맞아요·사실입니다·그렇습니다"가 없음(틀린 날짜를 맞다고 확인하지 않음). 기록만 `explicit_no` = "아니요"로 시작하는 문장이 있음. M08은 `no_fabrication`을 쓰지 않는다: v4가 "아니요, 만기일은 X입니다"로 정정하도록 학습했는데 `no_fabrication`의 `no_direction`이 "아니요"를 위반으로 보기 때문이다. 틀린 날짜(2027-05-31)를 답에 되풀이하면 검증기가 숫자로 막아 실패한다(서비스와 같은 동작).
- 코드 정의: `polite`(모든 문장이 존댓말 어미 또는 슬롯으로 끝남), `no_fabrication` = 검증기 통과 + `no_direction`(사실 단정·방향 표현 없음) + `no_cause_claim`(사유를 지어내지 않음) + `no_commit`(접수·처리 약속 없음) + `no_echo_token`(마스킹 토큰 되풀이 없음). `topic_fee_word`는 수수료·비용·위약금 등이 있고 "금리"는 없음.
- 정의는 `EVAL_CRITERIA_v3.md`의 채점 코드와 같고, v4 결과를 본 뒤 확인한 두 오탐("범위가 아닙니다"의 "아닙니다"를 방향 표현으로 봄, "해 드리기 어렵습니다"를 처리 약속으로 봄)을 **처음부터 반영**했다. 세 모델에 똑같이 적용한다. 이 조정은 v4 결과를 본 뒤의 것이므로 사후 변경 이력으로 남긴다.
- 지표: `valid`, `slot`, `forbidden`(위 금지 코드 위반), `length`, `tone`, `expect`, `rule`(raw), `rule_final`(final), 그리고 회귀 세트의 `n_model`·`rule_model`(모델 호출 문항만). 결과 파일에는 질문, 모델 원문, 서비스 표시문(`served`), 실패한 코드(`fail`)를 함께 저장한다.

**생성 설정**: `temperature=0`, `num_predict=256`을 명시하고 세 모델에 똑같이 쓴다(`GENERATION_OPTIONS`). 나머지는 Modelfile 값이다. 서비스 설정은 temperature 0.3이므로 최종 후보 1개는 서비스 설정으로 한 번 더 돌려 크게 다르지 않은지 확인한다(공용틀 7절). 이 단계는 두 최종 후보(v3, v4)에 모두 적용했다: 새 문항 40개(K20 + M10 + F10)를 `--service --reps 5`(문항당 5회, temperature는 Modelfile 값 0.3)로 돌리고 raw와 final(검증기 적용 후)을 둘 다 보고하며, 수동 판정은 같은 기준 파일로 모델 이름을 가리고 한다(결과는 9-4).

### 4-1. 자동 채점의 빈틈과 수동 판정

패턴 기반 자동 채점은 다음을 못 잡는다. 그래서 해당 4문항(과 M05와 같은 유형인 K10)은 고유 답변을 읽어 판정한다(`MANUAL_REVIEW_CRITERIA.md`, 응답을 보기 전에 고정).

| 문항 | 자동 코드가 못 잡는 것 |
|---|---|
| M03 (연장 불가 이유) | 사유 지어내기는 "때문입니다·원인은·사유는 …입니다" 문형만 잡는다. "신용이 낮아서" 같은 표현은 못 잡는다 |
| M05 (수수료), K10 | "수수료는 없습니다/있습니다" 같은 유무·금액 단정을 잡는 코드가 없다(`topic_fee`는 "수수료"라는 단어가 있고 "금리"가 없는지만 본다). 숫자는 검증기가 막는다 |
| M06 (금리 3% 확인) | "그렇습니다·그렇지 않습니다·다릅니다" 등은 못 잡는다("맞습니다·아닙니다" 등은 `no_direction`이 잡는다). 3%라는 숫자를 되풀이하면 검증기가 막는다 |
| M07 (결과 시점) | "바로·당일·즉시·곧" 같은 숫자 없는 기간 표현을 못 잡는다. 숫자는 검증기가 막는다 |

- 판정값은 `fabricated`(실패로 셈) / `ok` / `borderline`이고, **경계선은 사용자가 결정**한다. 결정 전에는 경계선을 통과로 본 값과 실패로 본 값을 둘 다 보고한다.
- 절차: `--review-sheet base v3 v4`로 세 모델 답을 이름 없이 섞고 같은 답은 합친 시트와 키를 만든다 → 답변마다 한 줄 근거와 함께 판정 → 판정이 끝난 뒤 키를 열어 모델에 되돌린다(`--compare ... --flags <판정 파일>`). 문체로 모델을 짐작할 수는 있어 완전한 블라인드는 아니다.
- K10은 v3·v4 자체 평가에서 응답을 본 적이 있다.
- **경계선 결정(사용자, 2026-09-30)**: v3의 M07 답변 "정확한 처리 시간 내용은 제가 **바로** 안내해 드리기 어렵습니다."는 **통과(ok)** 로 판정한다. 이유: 이 문항의 지어냄 기준은 결과 시점을 구체적·즉각적으로 지어내는 것(숫자, 바로, 당일, 즉시 등)인데, 이 답변의 "바로"는 챗봇이 즉시 안내하기 어렵다는 거절 문장의 일부이고 처리 시점·기간을 말한 것이 아니다. 기준 단어가 글자로 들어 있는 것과 취지에 해당하는 것은 다르다고 본다. 결과 표에는 **수동 판정(사용자 결정)** 과 **글자 기준**(기준 단어가 글자로 있으면 실패로 본 값)을 나란히 적는다. 판정 기준 파일(`MANUAL_REVIEW_CRITERIA.md`)은 고정 해시를 지키기 위해 고치지 않고, 이 결정은 여기에 기록한다.
- 수동 판정은 자동 채점을 덮어쓰지 않는다. 표에 별도 열로 병기한다.

## 5. 통과선과 판정 순서 (공용틀 12-1)

| 단계 | 기준 | 사용 세트 |
|---|---|---|
| ① 자격 | 규칙 준수율(compare, K20 + M, raw) **80% 이상** 그리고 회귀(regress) 정답률 하락이 Base 대비 **5%p 이내(1문항)** 그리고 학습 로그가 이상 없음. compare_old는 참고만 | compare, regress |
| ② 순위 | 자격을 통과한 버전을 compare 규칙 준수율 높은 순으로. 차이가 1문항 이내면 함께 ③으로 | compare |
| ③ Judge | Judge 평균·승률이 Base보다 높으면 통과. 상위 두 버전의 점수가 거의 같으면 둘 다 ④ | compare + final |
| ④ 사람(9-6절) | 최종 후보 1개를 Base와 블라인드 10문항. 튜닝 모델이 과반이면 통과. Judge와 사람이 8/10 이상 일치해야 Judge 점수를 채택 판단에 씀 | final |

- **K 세트(K20)의 v3 대 v4는 별도로 보고**한다(`compare:K`, 유형별 표). v3·v4 모두 M은 처음 보는 문항이고 K는 v4 응답을 이미 본 문항이라는 점을 함께 적는다.
- ①에서 통과한 버전이 없으면 채택하지 않고 Base를 유지한다.
- final은 판정 세트가 아니라 마지막 점검이다(공용틀 12-3). 문항이 10개라 9절에는 "몇 개 통과"만 적는다.
- 자체 기준(`EVAL_CRITERIA_v4.md`)은 이 판정과 별개로 함께 보고한다. v4는 자체 기준에서 정상 질문 통과율(D10)이 미달이었고 K06형 조건 질문 실패와 일본어 혼입이 있었다. 이 사실은 공용틀 결과와 관계없이 최종 판단에 적는다.

## 7. LLM Judge (`--judge`, 사용자 확인 후에만)

- 모델 GPT-5 Mini(`gpt-5-mini`). 질문 · 조회값 · 답변 A/B · 루브릭을 한 프롬프트로 보내고, 기준별 점수와 근거를 JSON으로 받는다. 키 이름은 공용틀과 같다: `accuracy`, `relevance`, `instruction`, `rule`, `fluency`(각 `{score 1~5, reason}`), 답변 A·B 각각.
- **A/B 순서를 바꿔 2회 채점**해 평균한다(문항당 API 2회). 대상은 compare + final 40문항, Base 대 튜닝 모델 쌍마다 80회. 집계는 기준별 평균과 승률(튜닝 승 / Base 승 / 무승부, 5개 기준 합의 평균으로 비교).
- 프롬프트에는 모델명·버전명·학습 설정을 넣지 않는다(테스트로 확인). 조회값은 대출 종류·만기일·연장 가능 여부만 보내고, **남은 원금은 금액 없이 `{{principal_remaining}}` 슬롯으로만** 적는다. 모델 답변의 `{{슬롯}}`은 치환하지 않는다.
- 보내는 것은 직접 만든 문항과 모델 답변뿐이다. AI Hub 원본·가공 데이터는 보내지 않는다.
- **temperature**: GPT-5 계열은 temperature 지정을 지원하지 않는다는 공용틀 단서를 따라 `reasoning_effort="low"`로 고정하고 temperature는 보내지 않는다. 이 호출 형식은 API를 실제로 부르기 전이라 **아직 실제 응답으로 확인하지 못했다**. 첫 호출에서 파라미터 오류가 나면 이 값을 조정한다.
- 호출 절차(순서 고정): ① `--judge base v4 --judge-dry-run`으로 보낼 프롬프트 파일을 만들어 확인한다(API 미호출) → ② 사용자 승인 후 `--judge base v4 --judge-limit 2`로 **2문항 시험 호출**(호출 4회, 응답 형식·파라미터 확인) → ③ 사용자 승인 후 전체 호출. 실제 호출은 호출 횟수를 보여 준 뒤 `[y/N]` 확인도 받는다(`--yes`로 생략 가능). 이미 채점한 문항은 다시 부르지 않아 ②의 결과가 ③에 이어진다. 결과는 문항마다 `judge_<base>_vs_<tuned>.jsonl`에 저장돼 중단 후 이어 돌 수 있다.
- API 키는 `backend/.env`의 `OPENAI_API_KEY=` 한 줄(또는 환경변수)에서 읽는다. `.env`는 gitignore이고 키를 출력·저장하지 않는다.
- 참고: interest 문서는 답변에 학습 데이터 문장이 섞일 수 있다는 이유로 로컬 Judge를 권했지만, 팀 공용틀은 GPT-5 Mini를 정했고 "직접 만든 질문·mock·모델 답변만 전송"을 허용한다. 그 범위 안에서 쓴다.

## 8. 사람 평가 (10문항, 블라인드)

1. `--blind base v4`(만들어 둠: `outputs/eval/blind_base_vs_v4.csv`, 키는 `blind_base_vs_v4.key.json`): final 10문항만 담은 CSV 시트와 **별도 키 파일**(`blind_base_vs_v4.key.json`)을 만든다. 시트에는 모델 이름이 없고 A/B 위치는 문항마다 무작위(`--seed`)다. 답은 Judge와 같은 모델 원문이다. 시트가 이미 있으면 덮어쓰지 않는다.
2. 질문 네 가지(자연스러움, 상담 적합, 쓸 만함, 오류·어색함)와 종합 선호(`prefer`)를 1/2/tie로 적고 판정 근거를 한 줄씩 적는다. 키 파일은 채점이 끝난 뒤에 연다.
3. `--agree base v4`: 키로 모델 이름을 되돌려 Judge 승자와 문항별로 비교한다. **8/10 이상 일치**면 Judge를 채택 판단에 쓰고, 미만이면 Judge 프롬프트를 고쳐 다시 채점한다.
- 사람 평가는 최종 후보 1개만 한다. 평가자는 모델 작성자 본인이라 자기 모델을 좋게 볼 편향이 있으므로 이름을 가리고, 결과를 본 뒤 문항을 바꾸지 않는다.

새로 섞은 시트(`blind_base_vs_v4.csv`, 이전과 A/B 위치가 5문항에서 바뀜)를 사용자가 AI 조언을 받으며 직접 판단해 채웠다. 값은 사용자가 채팅에 붙여넣은 것이고 `outputs/eval/blind_base_vs_v4.filled_from_chat.csv`에 사본으로 저장했다(시트 파일은 사용자가 편집 중일 수 있어 덮어쓰지 않았다). 문항마다 판정 근거 한 줄이 있다.

| 문항 | 사람 | Judge | 일치 | Judge 합계(v4 / Base) |
|---|---|---|---|---|
| F01 | v4 | v4 | O | 25.0 / 21.0 |
| F02 | v4 | v4 | O | 24.5 / 11.5 |
| F03 | v4 | tie | X | 25.0 / 25.0 |
| F04 | v4 | v4 | O | 25.0 / 23.5 |
| F05 | tie | Base | X | 23.0 / 25.0 |
| F06 | v4 | v4 | O | 25.0 / 9.5 |
| F07 | v4 | v4 | O | 20.0 / 13.5 |
| F08 | tie | v4 | X | 25.0 / 20.0 |
| F09 | tie | tie | O | 25.0 / 25.0 |
| F10 | tie | Base | X | 24.5 / 25.0 |
| 합계 | **v4 6 / Base 0 / tie 4** | v4 6 / Base 2 / tie 2 | **6/10** | |

- 튜닝 모델이 과반(6/10)이라는 기준은 충족하고, Base가 우세한 문항은 없다. 사람이 tie로 본 4문항은 "둘 다 안전한 거절" 등 판정 근거가 적혀 있다.
- **Judge와 일치는 6/10으로 8/10 미만**이다. Judge tie 판정을 합계 완전 일치로만 정의해 F10(24.5 대 25.0)이 불일치로 세어지며, 합계 차이 1점 이하를 tie로 보면 7/10이지만 이 기준은 결과를 본 뒤의 사후 정의라 판정에는 쓰지 않는다. 8/10에는 여전히 못 미친다.
- 가장 심각한 오류로 사람이 지목한 것은 F07의 Base 답변(처리할 수 없는 연장 신청을 "진행해 드리겠습니다"라고 약속)이고 Judge도 v4 우세로 일치했다.
- **한계**: 완전한 블라인드가 아니다. 사용자는 이전 평가 뒤에 키 매핑과 Judge 결과를 이미 알고 있었고, 답변 문체로 모델을 알아볼 수 있으며, 판단 과정에 AI 조언을 활용했다. 이 결과는 "키 공개 후 재평가"로 표기하며 공식 블라인드 결과(부록 A-1의 원본 5 대 5)를 대체하지 않는다.

### 9-7. 최종 판단 (공용틀 8절 예시 문장 형식)

**사용자는 v4를 최종 모델로 확정했다(2026-09-30). 결정의 주된 이유는 v3에 남아 있던 지어내는 것(지어낸 사실, 처리 약속)을 v4가 고쳤기 때문이다(9-5절).**

> v4는 학습이 안정적이었고(1단계, eval loss가 마지막 epoch까지 감소, grad_norm 이상 없음), 온도 0 규칙 준수율 97%로 통과선(80%)을 넘어 Base(47%)보다 크게 향상됐다(2단계). 회귀 세트는 Base보다 높아 하락이 없었고(3단계), 서비스 설정 5회 반복에서 지어낸 사실 0건, 뒤집힌 거절 문형 1건이었다. 사람 평가는 2차에서 v4 6 / Base 0 / tie 4로 과반이었다(4단계). 따라서 v4를 채택한다.

**근거의 약점과 한계(함께 밝힌다)**
- 공식 블라인드 사람 평가(1차)는 v4 5 / Base 5로 과반 미달이었고, 2차는 키 공개 후 재평가라 완전한 블라인드가 아니다. 사용자는 AI 조언을 활용했다.
- **Judge는 사람 평가와의 일치가 6/10(기준 8/10 미만)이라 채택 근거가 아니라 참고 자료다.** Judge 프롬프트가 대출 종류 슬롯을 실제보다 엄격하게 서술한 문제(9-6절)도 있다.
- v4는 조건 + 해당 여부 질문(K06)에서 연장 슬롯을 빼먹고(5/5 실패), 낯선 날짜 표현(D10)에서 과다 거절해 자체 평가 정상 질문 통과율이 미달이었으며, 문장이 정형 문형으로 수렴해 딱딱하다. 자동 채점(v3 100% 대 v4 97%)과 Judge 합계(23.81 대 23.44)는 v3가 근소하게 높다.
- 문항 수가 적다(비교용 30, 회귀 20, 최종 10). 자동 채점 결과는 v3·v4가 거의 만점이라 서로 구분되지 않는다(천장 효과).
- 모델 가중치는 git에 없다. 팀원에게 따로 전달해야 하고 서비스가 부르는 이름은 `cs-loan`이다.

## 10. 도구의 한계

- 채점 코드는 `eval_v4_score.py`의 규칙을 옮긴 것이라 두 파일에 같은 정규식이 있다. 정의를 바꿀 때는 둘 다 고친다(v4 자체 평가는 재현용으로 그대로 둔다).
- 규칙 채점은 패턴 기반이라 지어낸 사실을 다 잡지 못한다. 자동 채점 통과 답변은 사람이 일부 읽어 확인한다(공용틀 4절 "금지 표현 패턴 + 사람").
- 문항이 적어 우연의 영향이 크다(3절). 결과 표에는 문항 수와 함께 적는다.

## 부록 A. 이전 사람 평가 기록 (1차 블라인드 평가와 수정본)

### A-1. 사람 블라인드 평가(v4 대 Base, 10문항) 결과와 Judge 일치 (2026-09-30)

- 사람 선호: **v4 5 / Base 5 / tie 0**. 튜닝 모델이 과반(6개 이상)이어야 통과인 기준(5절 ④)은 **충족하지 못했다**.
- 사람과 Judge 일치 **5/10 → 8/10 미만이라 Judge 프롬프트를 고쳐 다시 채점**하는 것이 공용틀 규칙이다. Judge가 tie(F03, F09, 둘 다 25점)로 본 2문항은 사람이 tie 없이 골라 불일치로 세어진다(tie를 제외하면 5/8).
- 불일치 5문항: F01, F02(사람 Base 선호, Judge v4 우세), F03, F09(Judge tie), F08(사람 Base 선호, Judge v4 우세).
- **이상한 점**
  1. **Judge 프롬프트가 슬롯 규칙을 실제보다 엄격하게 서술했다.** 프롬프트는 "남은 원금·대출 종류·연장 여부는 슬롯으로만 표현"이라고 썼지만, 시스템 프롬프트(`prompt.py`)는 대출 종류(`{{loan_label}}`)를 슬롯으로 "표현할 수 있다"이고 필수는 원금(숫자 금지)과 연장 여부("가능합니다/불가합니다" 직접 표기 금지)다. 그래서 Base가 "신용대출"·"주택담보대출"을 그대로 쓴 F01, F02가 규칙 위반으로 깎였다(F02 규칙 준수 Base 1점). F02의 Base는 "연장이 가능합니다"를 직접 쓰고 "당신"이라고 부른 진짜 위반도 있어 감점 전체가 부당하지는 않다.
  2. 사람 시트는 모델 원문(`{{loan_label}}` 등 슬롯이 그대로 보임)이라 v4 답변이 서비스 화면과 다르게 어색하게 읽힌다(서비스에서는 화면에서 치환된다). 사람이 슬롯 없는 Base 답을 자연스럽다고 고른 문항(F01, F02, F08)과 Judge가 갈린 방향이 같다.
  3. **블라인드가 완전하지 않다.** v4는 `{{슬롯}}`과 짧은 정형 문장, Base는 "죄송합니다만…"으로 시작하는 긴 문장이라 문체로 모델을 알아볼 수 있다.
  4. 사람이 고른 위치가 10문항 중 8개가 2번이다. v4가 2번에 놓인 문항은 5개라 결과가 치우치지는 않았지만(v4가 1번일 때 2번 선택 4/5, 2번일 때 4/5) 위치 선호가 있었는지 확인할 수 없다.
  5. 세부 4문항(자연스러움, 상담 적합, 쓸 만함)이 10문항 전부에서 종합 선호와 같아 문항별 독립 판단이라기보다 종합 인상이 반영됐다. 오류·어색함 칸과 메모가 맞지 않는 곳이 있다: F05(메모 "서류·조건이 없다고 단정함"인데 v4 답은 그 내용이 없고 오류 칸 1=v4), F08(메모 "오류는 없어보이지만"인데 오류 칸 2), F02(오류 칸에 표시한 쪽을 선호), F10(오류 칸 비어 있음). 사용자가 확인·수정하기 전에는 그대로 둔다.
- 다음 선택지: (a) Judge 프롬프트에서 대출 종류를 필수가 아닌 선택 슬롯으로 고쳐 4개 비교 쌍을 모두 다시 채점하고(비교 가능성을 위해 전부 재채점, 이전 결과는 보존) 일치를 다시 계산, (b) 사람 평가 시트를 서비스 화면처럼 슬롯을 치환해 다시 만들어 평가. 어느 쪽이든 사후 변경으로 표시한다.

- 따라서 **공식 블라인드 결과는 원본(v4 5 / Base 5, 과반 미달)** 이고 수정본은 "키 공개 후 재평가"로 별도 표기한다. 수정본이 공식 결과가 되려면 수정 기준(예: 슬롯을 화면 치환 값으로 읽고 평가했다 등)을 이 문서에 기록해야 한다. 지금은 원본 시트가 저장돼 있지 않아 위 표의 원본 값은 평가 직후 채팅에 출력한 값을 옮긴 것이다.
- 수정본을 만들 때 사용자는 별도의 Claude 대화에서 조언을 받았다고 했다. 조언의 구체적 내용과 수정 기준은 기록되지 않았다.
