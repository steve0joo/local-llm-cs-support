# 모델 평가 가이드: cs-interest

> 강의자료 "QLoRA 모델 평가 방법"의 평가 틀을 이자/연체 에이전트에 맞게 옮긴다. 원 자료의 "사극체 능력"은 이 에이전트의 **상담 규칙 준수**(조회값만 쓰고, 금액은 슬롯으로, 모르면 상담원 안내)로 바꿔 읽는다.
> 핵심 원칙: **"잘 학습되었는가"와 "좋은 모델인가"를 구분한다.** loss가 내려간 것은 학습이 진행되었다는 신호일 뿐, 좋은 상담 모델이라는 뜻이 아니다.

## 평가의 네 질문

| # | 질문 | 도구 | 산출물 |
|---|---|---|---|
| 1 | 학습은 안정적인가? | 학습 로그(loss·grad_norm·learning_rate) | 학습 리포트 |
| 2 | 목표 능력(상담 규칙 준수)이 생겼는가? | Golden Set + 규칙 준수율 | Golden Set 결과표 |
| 3 | 기존 능력은 유지되는가? | 회귀 평가(Base vs QLoRA 같은 셋) | 회귀 비교표 |
| 4 | 사람이 보아도 좋은가? | LLM Judge + 사람 블라인드 평가 | Judge 점수표, 선호도 |

**최종 판단 문장:** "Base보다 상담 규칙 준수가 좋아졌고, 조회값 활용·정확성은 손상되지 않았으며, 사람이 보아도 쓸 만한가?"
이 문장에 모두 "예"일 때만 파인튜닝 모델을 채택한다. 아니면 Base(또는 이전 채택 모델)를 유지한다.

```
QLoRA 학습 → [1] 학습 로그 확인 → [2] Golden Set → [3] Base vs QLoRA 회귀 → [4] Judge + Human → 최종 판단
```

---

## 질문 1. 학습은 정상적으로 되었는가?

답변 품질이 아니라 **학습 과정의 안정성과 과적합 징후**를 본다.

| 지표 | 무엇을 보나 | 주의 신호 |
|---|---|---|
| train/loss | 학습 데이터 오차가 줄어드는가 | 너무 빠르게 0 근처로 가면 암기 가능성 |
| eval/loss | 검증(val) 데이터에서도 줄어드는가 | 줄다가 오르기 시작하면 과적합 → 그 직전 epoch 채택 |
| grad_norm | 안정된 범위에서 움직이는가 | 급증(스파이크), NaN, 0 근처 고정 |
| learning_rate | 설정한 warmup → cosine decay 모양인가 | 그래프 모양이 설정과 다름 |

**이 프로젝트에서의 방법**
- 학습 로그는 **로컬에만** 남긴다. W&B 같은 외부 서비스는 쓰지 않거나 오프라인 모드로만 쓴다(데이터 제3자 제공·국외 클라우드 금지 원칙). `train.py`의 `report_to="none"` 상태에서는 체크포인트의 `trainer_state.json`(`log_history`)과 콘솔 로그로 확인한다. 그래프가 필요하면 TensorBoard(로컬)를 쓴다.
- 확인 결과는 실험 폴더 `training/interest/outputs/<run>/settings.json`의 지표와 함께 기록한다.

**기존 실험 기록 (참고)**
| 실험 | train/loss | eval/loss | 판단 |
|---|---|---|---|
| run-20260928-aihub-only (2e-4, 3 epoch, 218건) | 1.29 → 0.83 | 0.90 | 학습은 안정적이었으나 **질문 2·3에서 크게 퇴행** — loss만으로는 좋은 모델인지 알 수 없다는 사례 |

## 질문 2. 목표 능력이 실제로 생겼는가? (Golden Set)

**학습 데이터에 없던 질문**으로 목표 능력을 검증한다.

### Golden Set 구성
- 30~50문항. 데모 고객 C002(정상)·C003(연체) 조회값으로 만든다(`evaluate.py`의 `DEMO_QUESTIONS`를 확장).
- **학습 데이터·합성 템플릿의 질문과 겹치지 않게** 표현을 바꾼다. 겹치면 외운 것과 배운 것을 구분할 수 없다.
- 질문 유형(`TRAINING_DATA_PLAN.md` 3절)을 골고루 넣는다: 이자 금액, 납부일, 연체 여부, 연체 대응, 이유, 용어, 금리, 계산, 잘못된 전제, 확정 요청, 다른 상품, 직원 확인, 상환·금리·납부 방식.
- 각 문항에 **기대 조건**을 적어 둔다. 예: "납부일 질문 → 답에 다음 납부일 날짜가 있어야 함".

### 규칙 준수 성공 기준 (4개 모두 충족해야 성공)
| 기준 | 내용 | 확인 방법 |
|---|---|---|
| 출력 형식 | 금액·금리 수치·마스킹 토큰·허용 밖 슬롯 없음, 연체 상태 질문엔 `{{overdue_amount}}` | `validate.is_valid` (자동) |
| 지어내지 않음 | 금리 %, 서류, 은행·앱 이름, 없는 시각·기간, 처리 완료 주장, 개인정보 요구 없음 | `evaluate.FORBIDDEN` (자동) + 사람 |
| 질문에 맞는 내용 | 유형별 기대 조건 충족(납부일 → 날짜, 연체 → 일수와 연체 금액 슬롯, 금리 → 수치 없이 상담원 안내, 방식 질문 → 조회값) | 기대 조건 검사(자동, 추가 예정) + 사람 |
| 상담 톤 | 존댓말, 2~4문장, 마크다운 목록·굵은 글씨 없음, 요약체("고객님께서는 ~하셨습니다") 아님 | 사람(일부 자동) |

**규칙 준수율 = 성공 응답 수 / 전체 문항 수** (원 자료의 Style Adherence Rate에 해당)

### 결과 기록
점수만이 아니라 **질문, Base 답변, QLoRA 답변, 판정 근거**를 함께 남긴다(`outputs/eval/<name>.jsonl`, `--compare`로 나란히 출력).

## 질문 3. 기존 능력은 유지되고 있는가? (회귀 평가)

규칙을 잘 지켜도 **질문에 맞게 답하는 능력**이 무너지면 좋은 파인튜닝이 아니다. 관점은 **"규칙 준수 + 내용 정확성"**이다.

| 예시 질문 | 좋은 답 | 나쁜 답 |
|---|---|---|
| 이자 빠지는 날이 언제예요? (C002) | "다음 납부일은 2026-10-15입니다." | "이자 빠지는 날은 {{interest_due}}입니다." → 날짜 질문에 금액 슬롯(Base에서 실제로 나옴) |
| 이번 달에 낼 이자가 얼마죠? | "납부하실 이자는 {{interest_due}}입니다." | "잔액과 금리를 확인한 후 알려드리겠습니다." → 조회값 무시(첫 파인튜닝에서 실제로 나옴) |

### 진행 방법
1. **회귀 셋 준비:** AI Hub test 분할(학습 미사용) + Base가 이미 잘하던 능력(슬롯 사용, 이자 정보 활용)을 보는 문항.
2. **Base·QLoRA 동일 채점:** 같은 질문, 같은 생성 설정(`do_sample=False`, `max_new_tokens=256`, 같은 채팅 템플릿).
3. **허용 기준 사전 합의:** 아래 지표가 Base 대비 **3%p 넘게 떨어지면 퇴행**으로 본다(원 자료 예시 기준 적용).
   - 검증 통과율, 슬롯 사용률, 유형별 기대 조건 충족률
   - 금지 표현은 **증가 자체를 불허**(지어낸 사실 1건 = 인수 즉시 불합격, PRD 인수 기준 4)

## 질문 4. 사람이 보아도 좋은 모델인가?

### LLM-as-a-Judge
같은 질문에 대한 Base와 QLoRA 답변을 같은 기준으로 1~5점 채점한다.

| 기준 | 내용 |
|---|---|
| 정확성 (Correctness) | 이자 정보·슬롯과 맞는가, 지어낸 사실이 없는가 |
| 적합성 (Relevance) | 질문에 답했는가 |
| 지시 준수 (Instruction Following) | 시스템 프롬프트 규칙(슬롯만, 모르면 상담원)을 지켰는가 |
| 상담 규칙 (Style Adherence) | 금리 수치·서류·처리 주장·개인정보 요구가 없는가 |
| 자연스러움 (Fluency) | 존댓말, 간결, 어색하지 않은가 |

**운영 규칙**
- Judge 모델은 **평가 대상과 다른 모델**을 쓰고 temperature 0으로 고정한다.
- Judge는 먼저 나온 답·긴 답을 선호하는 경향이 있으므로 **A/B 순서를 바꿔 2회 채점 후 평균**한다. 루브릭은 고정한다.
- **Judge도 로컬 모델만 쓴다.** 평가 답변은 AI Hub로 학습한 모델의 출력이라 학습 데이터 문장이 섞여 나올 수 있다. 외부 API에 보내지 않는다. 로컬 후보: 이 노트북에 올릴 수 있는 다른 모델(예: Qwen3-8B 4bit). 적당한 로컬 Judge가 없으면 이 단계는 생략하고 사람 평가로 대신한다.
- 절차: A/B 순서 바꿔 2회 채점 → 평균 → Golden Set 전체 집계 → 기준별 평균·승률 비교.

### Human Evaluation
- **모델 이름을 숨기고** A/B로 보여 준 뒤 선호도를 기록한다.
- 질문: 어느 답이 더 자연스러운가? 상담 목적에 더 맞는가? 실제로 쓸 만한가? 내용 오류나 어색함은 없는가?
- 결과: **QLoRA Win / Base Win / Tie**
- PM 인수 기준(주제 적합 · 지어내지 않음 · 존댓말 톤, PRD 인수 기준 3)을 O/X로 함께 매긴다.

## 실습 순서 (한 번의 평가 사이클)

1. **Golden Set 작성:** 30~50문항, 학습 데이터·템플릿과 겹치지 않게, 문항별 기대 조건 포함
2. **두 모델 응답 생성:** 같은 질문·같은 생성 설정(`evaluate.py --name base` / `--name <run> --adapter ...`)
3. **자동 채점:** 검증 통과, 금지 표현, 기대 조건, 규칙 준수율
4. **Judge 점수 산출:** 로컬 Judge 사용 시, A/B 2회
5. **사람 평가:** 블라인드 A/B, PM 기준 O/X
6. **최종 판단 작성:** 개선·퇴행·한계를 네 질문에 대한 답으로 정리

### 최종 판단 예시
> "본 QLoRA 모델은 학습 로그상 안정적이었고, Golden Set 규칙 준수율이 Base 대비 X%p 향상되었다. 회귀 지표 하락은 허용 기준(3%p) 이내이며 금지 표현은 0건이다. 사람 블라인드 평가에서 QLoRA Win N / Base Win N / Tie N으로 채택한다(또는 채택하지 않는다)."

| 검증 통과율, 슬롯 사용, 금지 표현, 길이 | ✅ 있음 |
